# 402Lab MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Invoke the `tdd` skill before the first line of code of every task.

**Goal:** Conta de consumo para agentes de IA: allowance com tetos, pagamento por chamada via x402 em USDC na Solana devnet, split em lote para provedores, extrato mensal, acompanhados por web e app.

**Architecture:** Monorepo pnpm. `apps/api` (Fastify 5 + `@x402/fastify`) vende 3 serviços atrás do 402 com `payTo` = tesouraria, aplica a política da allowance no hook `onAfterVerify`, grava o ledger no `onAfterSettle` e um worker distribui o split em uma tx com N `TransferChecked`. `packages/mcp` é o pagador (carteira de sessão em arquivo). `apps/web` (Next 16) e `apps/mobile` (Expo 57) leem a API.

**Tech Stack:** Node 24, TypeScript, pnpm workspaces, Fastify 5.12, `fastify-type-provider-zod`, Zod 4, Drizzle + Postgres 16, `@x402/*` 2.28.0, `@solana/kit` 8.4, `@solana-program/token`, `@modelcontextprotocol/sdk` 1.32, Next.js 16.4, Expo SDK 57, Vitest 5, jest-expo.

**Spec:** `.claude/docs/specs/2026-10-10-402lab-allowance-design.md`

**Comportamento:**
- **Fatos do spike (.claude/docs/research/04):** abort no `onAfterVerify` responde 402 e o `reason` vai em `payment-required.error`; o hook roda também com `isValid=false`; **exceção dentro do hook é engolida e o pagamento segue aprovado** → todo o corpo do hook em try/catch retornando `{ abort: true, reason: "policy_unavailable" }`; no settle o `transportContext.request.path` dá o serviço (`routePattern` só existe no verify); handler ≥400 não faz settle.
- `onAfterVerify`: só avalia quando `context.result.isValid`; pagador = `context.result.payer`; `findAllowanceBySession`; se existe, `evaluateAllowancePolicy(policy, BigInt(context.requirements.amount), await spentToday(...))`; negado → `{ abort: true, reason }` e, se `daily_cap_exceeded`, publica `allowance.cap_reached`.
- `onAfterSettle`: `recordPayment` com `context.result.transaction` como `txSignature`; `serviceId` vem do path no `transportContext` (formato confirmado no spike); duplicado (`tx_signature` unique) é ignorado sem erro; publica `payment.settled` para o owner da allowance (ou `null` se avulso).
- `spentToday`: soma `amount` com `settled_at >= início do dia UTC de now`.
- Auth SIWS: `GET /auth/nonce?address=` cria nonce (expira em 5 min); `POST /auth/verify {address, signature, message}` confere a mensagem exata `402Lab login\nAddress: <address>\nNonce: <nonce>`, verifica Ed25519 com `@solana/kit` (`verifySignature` + `getPublicKeyFromAddress`), consome o nonce (uso único) e seta cookie httpOnly `session` (JWT 7 dias, `SameSite=Lax`, `Secure` em produção). `POST /auth/pair` (autenticado web) devolve token `mobile` de 30 dias.
- Allowances: `POST /allowances {agentName, sessionAddress, perCallCap, dailyCap}` (autenticado; `sessionAddress` validado com `isAddress`; duplicado → 409), `GET /allowances`, `GET /allowances/:id` (outro owner → 404), `PATCH /allowances/:id {status?, perCallCap?, dailyCap?}` → publica `allowance.updated`, `GET /allowances/by-session/:address` público com `{status, perCallCap, dailyCap, spentToday}`.

- Eventos: `GET /events` (SSE, autenticado, só eventos do owner via `bus.subscribe`, heartbeat a cada 15 s) e `GET /allowances/:id/payments?after=<paymentId>` (polling do mobile, até 50 itens, ordem crescente).
- Extrato: `GET /allowances/:id/statement?month=YYYY-MM` → `{ month, totals: { amount, cardEquivalent, byService[], byProvider[] }, payments[] }` com valores em string atômica; mês inválido → 400.
- Waitlist: `POST /waitlist {email}` → 201; e-mail repetido → 201 (idempotente, não revela existência); rate limit `@fastify/rate-limit` 5/min por IP.
- Demo on-ramp: `POST /onramp/simulate {sessionAddress, amount}` (autenticado, owner da allowance, máximo `5_000_000n`) → tesouraria transfere USDC devnet e devolve a assinatura; rota só registrada quando `NETWORK === SOLANA_DEVNET`.

**Interfaces — Produces:**
```ts
// splits/transaction.ts
export const buildSplitTransaction = (input: { treasury: KeyPairSigner; payouts: PayoutLine[]; mint: Address; latestBlockhash: { blockhash: Blockhash; lastValidBlockHeight: bigint } }): Promise<{ signedTransaction: ...; signature: string }>;
// para cada payout: getCreateAssociatedTokenIdempotentInstruction (payer = treasury) + getTransferCheckedInstruction (decimals 6)
// splits/worker.ts
export type SplitChain = { latestBlockhash(): Promise<...>; send(tx): Promise<void>; signatureStatus(signature: string): Promise<"confirmed" | "failed" | "unknown">; blockHeight(): Promise<bigint> };
export const runSplitRound = (dependencies: { db: Database; chain: SplitChain; treasury: KeyPairSigner; catalog: Service[]; bus: EventsBus }): Promise<void>;
export const startSplitWorker = (dependencies, intervalMs = 30_000): () => void;
```

**Algoritmo de `runSplitRound`** (exatamente nesta ordem):
1. **Reconciliar lotes `pending` com `tx_signature`**: `signatureStatus` → `confirmed` marca `confirmed` + evento `split.confirmed`; `failed` ou (`unknown` e `blockHeight() > last_valid_block_height`) marca `failed`, zera `split_batch_id` dos pagamentos do lote + evento `split.failed`; `unknown` dentro da validade → não faz nada nesta rodada.
2. **Se ainda há lote `pending`, encerra a rodada** (`ponytail:` um lote em voo por vez; paralelizar quando o volume pedir).
3. Seleciona pagamentos `split_batch_id is null` e `upstream_status = 'ok'`; nenhum → encerra.
4. `computeSplit` por pagamento com as regras do serviço → `aggregatePayouts` → `chunkPayouts(…, 8)`; usa só o primeiro chunk e só os pagamentos que o compõem (`ponytail:` se houver mais de 8 recebedores, sobra para a próxima rodada).
5. Transação de banco: cria `split_batches(pending)`, insere `payouts`, marca `split_batch_id` dos pagamentos.
6. Busca blockhash, monta e assina; **grava `tx_signature` e `last_valid_block_height` antes de enviar**.
7. `send`. Erro de envio não marca nada: a reconciliação da próxima rodada decide.

**Testes (com `SplitChain` fake em memória):**
- 3 pagamentos de 2 serviços → 1 lote, payouts agregados corretos, assinatura gravada antes de `send` ser chamado (o fake verifica no banco dentro de `send`).
- `send` lança → lote segue `pending` com assinatura; próxima rodada com status `confirmed` → `confirmed`, sem reenvio (fake conta `send` = 1).
- status `unknown` e altura acima da validade → `failed`, pagamentos liberados, rodada seguinte cria lote novo.
- status `unknown` dentro da validade → nada muda, nenhum lote novo.
- pagamento com `upstream_status = 'failed'` não entra em lote.
- `buildSplitTransaction`: instruções na ordem create-ATA, transfer por recebedor; valores e decimais corretos (decodificar a mensagem compilada no teste).
- `GET /splits` (autenticado) lista lotes com link do explorer.

Verde + cobertura. Smoke manual na devnet: `pnpm --filter @402lab/api split:once` (script que roda uma rodada contra a devnet) e colar a assinatura no PR. Commit `feat(api): distribute provider splits in batched solana transactions`.
